# 定位与总体设计

本文回答三个问题:这个项目是什么、和谁不同、按什么路线做。领域模型的细节在 [super-agent.md](super-agent.md),本文只讲定位与边界。

## 一句话

> **别人的 AI 手边有一个云电脑;Mika 手边的"云电脑",是用户口袋里这台真手机。**

它不是一个聊天机器人加一堆定时任务,而是一个**住在手机里的工单系统**:多来源的请求进门禁、领授权、开工单,后台虚拟屏上真正动手干活,干完或卡住才来找人。用户正常用手机,它在另一块屏上并行工作。

## 身份

| | 大脑在哪 | 手在哪 | 任务模型 | 主动性的边界 |
|---|---|---|---|---|
| Grok bot | xAI 云 | X 平台内 | 单轮 @ 响应 | 平台黑盒 |
| Meta Muse | 每用户一个云 VM | 云 VM 里的服务 | 会话 | 云端策略 |
| nanoMuse | 你的设备(多个) | 截图+坐标点按,基本要前台 | 目标+例程 | Sentinel 审批 |
| DSH super-agent | 你的桌面 | 桌面仓库,产出 PR | 工单+Mandate | 门禁+准入表 |
| **本项目** | **手机 + relay** | **用户的手机:后台虚拟屏,真实身份** | **工单+Mandate,多来源** | **门禁+准入表,本机执行** |

三件只有这个组合能做的事:

1. **后台并行执行。** 虚拟屏让 agent 在用户正常用手机的同时在另一块屏上操作 App。nanoMuse 的手要前台浮窗,云电脑根本没有你的手机。
2. **真实身份执行。** 登录态、SIM、本地 App、支付,只在真机上存在。云电脑是无根之木,替人办事处处断链。
3. **工单制多来源。** 群消息、定时、通知、电脑 MCP 都能进票,门禁授权后才动手,多票并行互不污染。现有手机 agent 没有这个模型。

产品名保持 Mika(尊重上游与已有认知);这套能力对外的身份是**「Mika 分身」**——手机即分身:你不在场时,它以你的身份、在你的设备上、按你授权的范围行事。

## 架构:五层与分工

```
┌──────────────────────────────────────────────────┐
│ 渠道层 · relay 侧(不在手机上)                       │
│   飞书 / Telegram / 钉钉 / 企微 bot 长连接 · Web 控制台 │
│   消息 → Trigger 帧(出站 WSS 推给手机);回复帧发回渠道  │
├──────────────────────────────────────────────────┤
│ 领域层 · 手机 core/superagent(唯一写者 Engine)       │
│   Source → Trigger → Thread → Eval → Ticket → Assignment │
│   门禁(名单/准入表) · Mandate · 处置账本 · 看门狗      │
│   Router(批量判决,不执行) · 效果队列(先落账后执行)     │
├──────────────────────────────────────────────────┤
│ 执行层 · Mika 本体(不改动)                          │
│   AgentLoop → 虚拟屏 / 无障碍 / 浏览器 / 沙箱 / 知识 / 技能 │
├──────────────────────────────────────────────────┤
│ 界面 · 面板(person 阶段沉顶) · 系统通知 · 策略设置     │
└──────────────────────────────────────────────────┘
```

每个角色跑在哪、为什么:

| 角色 | 跑在哪 | 原因 |
|---|---|---|
| bot 连接器 | relay | 24 小时在线;手机息屏、断网、杀进程都不丢消息;手机永不暴露公网 |
| 门禁 + Router | 手机 | 授权是本机的事;批量判决摊薄 token;名单在设备上,不进云 |
| Worker | 手机 | 手就是这台手机;复用 TaskCenter 派工与现有全部能力 |
| 状态库 | 手机 | 票、Mandate、送达凭据本地落盘;relay 只转发帧,不看内容 |
| 面板 | 手机 App / Web | 只把卡在「人」的票顶给人,正常干活的沉底 |

## 安卓作为执行电脑:一等约束

云电脑从不睡觉,安卓会。这些不是实现细节,是设计输入:

| 约束 | 对策 | 已有基础 |
|---|---|---|
| 进程随时可能被杀 | 票必须跨进程死亡存活;恢复靠自查,不重放外部动作 | RunRecovery、JSON 原子落盘 |
| Doze 与后台限制 | 精确闹钟 + 前台服务 | TriggerEngine 已处理闹钟与时区 |
| 消息必达 | relay 侧缓冲 Trigger;效果队列带送达凭据 | tools/relay 出站 WSS、Outbox 账本 |
| 屏幕冲突 | 后台虚拟屏是常态,前台接管是例外 | 虚拟屏 + 接管机制 |

设计口诀:**票比进程活得久,凭据比执行活得久。**

## 用户看到的三个场景

**A. 快速路径(聊天,不开票)**——飞书群 @Mika:「明早北京到上海的高铁还有票吗」→ 门禁过(名单内点名)→ Router 直接答,或当只读快查派下去。秒级,不产生工单。

**B. 工单路径(任务)**——「盯着这趟车,放票就提醒我,可以的话帮我下单」→ 开票,Mandate 写明:只许 12306、只读监控、下单动作必须人确认 → 后台按例检查 → 到点回群里问一句,等确认后下单再回报。全程用户可停、可改、票结束留完整账。

**C. 例程路径(Muse 式,但带手)**——「每天早上七点把我的未读整理成简报发群里」→ 例程票每天执行:读屏收集、整理、发简报,末尾附「要不要我顺手回这两条?」。主动冒泡必须有 Mandate 授权的固定范围,不是自由发挥。

## 铁律

从 DSH 与 nanoMuse 的实践提炼,全程不改:

1. **授权在代码,不在提示词。** 门禁、Mandate、重验是 Engine 的代码;模型只判路由,判决过宿主校验。
2. **先落账,后执行。** 每个决定先写状态库;副作用带凭据,重启自查恢复。
3. **转引用,不转述。** Router 只传 Trigger 引用与路由事实(附注 ≤30 词);工人读原文。
4. **屏幕是最后一级梯子。** 技能/接口 → 带登录抓取 → 内置浏览器 → 屏幕;走屏幕前一句话告知。
5. **先观察,后自动。** 新来源、新规则一律 Observe 起步,审计「本会接受」日志后再开 Auto。
6. **域层测试:源码 ≥ 1:1,回放式评测。** 录一次真实模型轨迹,CI 断网重放;领域规则是资产。

## 路线图(五阶段)

| 阶段 | 内容 | 验收 |
|---|---|---|
| 1. 领域规则 | 处置账本、结构化报告状态机、机器门、两套判决、评估超时、开票去重、handback/ack | 测试:源码 ≥ 1:1;回放评测绿 |
| 2. 执行接入 | SuperExecutor 适配器(scope→能力子集)、效果队列安卓化、看门狗 | 真机全链路:杀进程后票状态完好,消息不重发 |
| 3. 渠道 | relay 侧 bot 连接器(先 Telegram 或飞书);本机通知来源;回复走 Outbox | 新来源接入不改 core;手机离线不丢 Trigger |
| 4. 策略与界面 | 名单/准入表/模式设置;面板阶段表;person 通知 | 面板只显示需要人的票 |
| 5. 放开 | Observe 审计后逐来源开 Auto;人格与记忆调教 | Observe 日志人工审计通过 |

## 我们不做什么

- **不碰微信个人号协议**:封号红线;合规渠道(飞书/钉钉/企微/Telegram)已够用,微信场景留给企业微信路线。
- **不做云执行**:定位即本地;relay 是哑的路由器,不是脑子。
- **不靠提示词做安全**:警告文字拦不住注入,授权只认代码。
- **不重造 Mika 已有的东西**:记忆、知识、技能、风险审批、送达账本、恢复机制全部复用;领域层只管「接活、授权、派工、收账」。
